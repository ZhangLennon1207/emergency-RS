# 可信遥感损毁评估与应急研判多智能体系统全过程实施方案

## 1. 文档目的

本方案用于指导项目从当前前端演示版本，逐步发展为能够接入比赛联调版 Agent1～Agent4、保存真实任务数据、执行可信校验并生成报告的完整系统。未来如需把量化评估从 Agent1 中独立出来，可再演进为五智能体版本。

项目采用“先讨论确认、再分阶段实施”的方式。每个阶段完成后进行验收，确认无误后再进入下一阶段，避免前端、后端和 Agent 团队同时修改同一套数据结构。

---

## 2. 最终项目定位

### 项目名称

可信遥感损毁评估与应急研判多智能体系统。

### 当前比赛联调版业务闭环

```text
创建研判任务
→ 上传灾前、灾后遥感影像
→ Agent1 建筑/道路分割、损伤评估、结构化证据和复核标志
→ Agent2 基于灾前/灾后原图生成英文变化描述
→ Agent3 将英文描述拆成原子 Claims 并逐条校验
→ Agent4 汇总可信事实、统计与复核标志，生成中文报告
→ 前端展示、下载和归档
```

### 当前四智能体职责

| Agent | 名称 | 核心输出 |
| --- | --- | --- |
| Agent1 | `agent1_visual_evidence` | 建筑/道路分割、实例损伤、融合图、证据账本、场景统计、模型置信度和复核标志 |
| Agent2 | `agent2_change_description` | Qwen2.5-VL-7B + LoRA 生成的英文变化描述 |
| Agent3 | `agent3_evidence_verification` | 原子 Claims、逐条校验状态、证据引用、理由、建议修正和校验后英文描述 |
| Agent4 | `agent4_report_generation` | 基于可信事实、场景统计和复核标志生成的中文 JSON/Markdown 报告 |

### 后续五智能体演进

用户最初规划的独立“损伤量化评估智能体”可在比赛联调版稳定后，从 Agent1 的统计能力中拆分出来。届时采用新的 `pipeline_version`，不能直接覆盖当前四智能体编号。

前端必须根据 `capability` 和 `pipeline_version` 展示结果，不能假设某个编号永远对应同一能力。

### 当前模型类别编码

交接文档明确的 Agent1 像素级类别为：

```text
0 = 背景
1 = 无损建筑
2 = 轻微损伤
3 = 严重损伤
4 = 摧毁
```

因此当前比赛版是“四种建筑状态 + 背景”，不是“五个建筑损伤等级”。前端现有五级 Mock 图例需要在正式联调前修正，或通过版本化映射兼容未来五级定义。

道路状态编码为：

```text
0 = 背景
1 = 完好道路
2 = 疑似受影响道路
```

## 3. 团队边界

### 前端负责

- 任务创建、影像选择和上传交互
- 四智能体比赛流水线执行状态展示，并预留未来能力扩展
- 灾前灾后影像对比
- 建筑 Mask 和损伤 Mask 图层展示
- 损伤量化图表
- 灾情描述与 Claim 展示
- 证据校验和人工复核界面
- 报告预览、下载和状态管理
- 加载、失败、重试、空数据等页面状态

### 后端负责

- FastAPI 接口
- 用户请求校验
- 任务状态机
- PostgreSQL 数据读写
- MinIO 或 OSS 文件管理
- Agent 调度和结果落库
- 报告文件下载
- 日志、错误码和权限控制

### Agent 团队负责

- 影像预处理和模型推理
- Agent1～Agent4 内部实现
- 每个 Agent 输入、输出符合约定格式
- 输出文件和结构化 JSON
- 模型版本、运行时间和错误信息

### 重要原则

- 前端不能直接连接数据库。
- Agent 不直接向业务数据库写表。
- Agent 结果统一返回给后端，由后端落库和上传文件。
- TIFF、Mask、模型权重和报告文件不保存到 PostgreSQL。
- 前端不依赖 Agent 本地目录结构，只依赖 API 返回的数据和文件 URL。

## 5. 补充强制要求：从现有双智能体到四智能体闭环

Agent1 和 Agent2 已完成 v1.0，Agent3 和 Agent4 正在接手构建。前后端必须先支持 Agent1/2 独立运行，再自然扩展为四智能体完整闭环。

### 5.1 成功结果必须包含

- 灾前原图和灾后原图。
- 建筑总数。
- 受损建筑数。
- 建筑受损比例。
- 受影响道路比例。
- 场景风险等级。
- 人工复核标记。
- 融合叠加图。
- 视觉对比图。
- 可选的建筑结果图。
- 可选的道路结果图。
- 英文灾情变化描述。
- 每个智能体的运行状态、执行时间和错误信息。

### 5.2 任务状态必须增加部分成功

任务总体状态统一支持：

```text
queued
running
partial_success
pending_review
completed
failed
cancelled
```

如果一个智能体失败、另一个智能体成功：

1. 后续可以独立运行的智能体应继续执行。
2. 任务最终标记为 `partial_success`。
3. 前端展示已经获得的结果。
4. 前端明确指出失败的智能体及错误原因。
5. 缺失结果区域显示“未生成”，不能伪造默认值。

### 5.3 未校验描述必须明确标记

在证据校验智能体尚未接入时，文字描述必须显示：

> 模型生成的变化描述，尚未经过证据校验。

不能将尚未验证的文字显示为“可信结论”或“正式研判结论”。

Agent3 接入后，该提示由 Agent3 的 Claim 校验结果替代。

### 5.4 前端任务流程

第一版真实联调流程为：

```text
选择灾前图和灾后图
→ 点击开始分析
→ 调用创建任务接口
→ 保存 job_id
→ 排队中
→ 视觉分析中
→ 文字描述中
→ 完成 / 部分成功 / 失败
→ 展示原图、可视化结果、核心指标和描述
```

前端必须以 `job_id` 作为任务查询和页面恢复依据。刷新页面后，应能够根据 URL 或本地保存的 `job_id` 重新查询后端状态。

### 5.5 GPU 串行执行要求

连续提交两个任务时：

- 两个任务必须按提交顺序排队。
- 不允许两个 GPU 模型同时占用同一张 GPU。
- 前端应展示队列状态和可选的队列位置。
- 后端必须保证串行消费，而不能只依靠前端禁止重复点击。

第一版推荐使用一个 GPU Worker，任务并发数设置为 1。

### 5.6 上传拒绝规则

以下输入必须在进入 Agent 前被明确拒绝：

- 非图片文件。
- 无法解码或已经损坏的图片。
- 超过允许体积的图片。
- 灾前图和灾后图尺寸不一致。
- 缺少灾前图或灾后图。

建议前端做一次快速校验，后端再做一次强制校验。后端校验结果是最终依据。

错误响应必须包含稳定错误码和用户可理解的信息，例如：

```json
{
  "code": "IMAGE_SIZE_MISMATCH",
  "message": "灾前图与灾后图尺寸不一致",
  "details": {
    "pre_image": [1024, 1024],
    "post_image": [2048, 2048]
  }
}
```

### 5.7 成果文件访问安全

- 前端只能接收 HTTP/HTTPS Artifact URL。
- API 不得返回 `C:\...`、`/home/...` 等本地绝对路径。
- 文件保存在 MinIO、OSS 或后端受控目录。
- 私有文件使用临时签名 URL。
- 数据库保存 `object_key`，不保存机器相关的绝对路径。

### 5.8 CORS 配置

后端通过 `FRONTEND_ORIGINS` 配置允许访问的前端地址，例如：

```text
FRONTEND_ORIGINS=http://localhost:5173,https://example.github.io
```

生产环境禁止无条件允许所有来源。React、Vue 或其他前端框架均使用同一套 HTTP API。

### 5.9 流水线版本与能力映射

交接文档确认当前比赛联调版采用以下四智能体编号：

| Agent | capability | 当前职责 |
| --- | --- | --- |
| Agent1 | `visual_evidence` | 建筑/道路分割、实例损伤、融合图、统计、证据账本和复核标志 |
| Agent2 | `change_description` | 根据灾前/灾后原图独立生成英文描述 |
| Agent3 | `evidence_verification` | 英文 Claims 拆分、逐条证据校验和修正 |
| Agent4 | `report_generation` | 使用可信事实和场景统计生成中文报告 |

为了兼容未来拆分量化智能体的版本，前端和数据库不能只依赖 Agent 编号判断功能。接口应同时返回：

```json
{
  "agent_code": "agent2",
  "capability": "change_description",
  "display_name": "灾前灾后遥感灾害变化描述生成智能体",
  "pipeline_version": "competition-four-agent-v1"
}
```

前端根据 `capability` 决定展示位置，根据 `display_name` 展示名称，使用 `agent_code + pipeline_version` 跟踪具体实现。

### 5.10 补充验证标准

- 已知正确图像对可以从网页上传并完成当前两个智能体推理。
- 网页核心数值和文字描述与直接执行现有脚本的结果一致。
- 连续提交两个任务时按顺序排队，不同时占用 GPU。
- 非图片、损坏图片、超大图片和尺寸不一致图片被明确拒绝。
- 单个智能体失败时展示 `partial_success`、已有结果和可理解的错误。
- 所有图片通过安全 Artifact URL 访问。
- API 和页面均不暴露本地绝对路径。

## 6. 已发现的真实项目资产

项目目录中已经存在可直接支撑前端设计和接口契约的真实材料：

- Agent1 固定20条输出：20条全部成功，包含建筑、道路、融合图、证据账本、统计摘要和复核标志。
- Agent2 同样20条输出：与 Agent1 的 `sample_id` 完全匹配，包含英文描述、原始响应、提示词快照和运行清单。
- Agent2 配对消融实验：包含140条成功记录及自动 Claims，但盲审尚未完成，只能作为实验和 Agent3 测试资产。
- Agent1～Agent4 两份交接文档：用于确认角色边界、字段语义、可信校验规则和报告生成规则。

当前推荐用 `EARTHQUAKE-TURKEY_003679` 建立第一套真实前端 Mock。该样本同时具备高风险建筑/道路结果、人工复核标志和存在推断偏差的 Agent2 文本，能够完整演示后续 Agent3 校验价值。

完整路径、数量、Schema 和限制见 `docs/project-data-inventory.md`。这些发现意味着阶段0不必继续凭空设计字段，应优先从真实 JSON 生成正式 API 契约。

## 7. 总体技术架构

```text
React 前端
    │
    │ HTTP / WebSocket
    ▼
FastAPI 后端
    ├── PostgreSQL + PostGIS：任务、状态、统计、Claim、报告元数据
    ├── MinIO / OSS：遥感影像、Mask、图表、JSON、Markdown
    ├── Redis：异步任务队列和临时进度
    └── Agent 编排服务
            ├── Agent1
            ├── Agent2
            ├── Agent3
            └── Agent4
```

开发阶段允许先不使用 Redis。后端可以通过后台任务或简单任务执行器完成第一轮联调，确认模型耗时和并发需求后再决定是否引入 Celery、RQ 或其他任务队列。

## 8. 全过程实施阶段

   - 地震

- API 契约文档
- 枚举字典

- JSON 示例能够完整覆盖五个 Agent。

### 讨论确认点

- 当前 Mask 类别是否保持“背景 + 四种建筑状态”

- 未来是否仍需要拆出独立损伤量化智能体

VITE_USE_MOCK=true

- Alembic 可以从空数据库创建所有表。
- Swagger 中可以完成基础接口测试。

## 阶段 5：Agent1 和 Agent2 首轮接入

### 目标

接入已经完成 v1.0 的视觉证据智能体和英文变化描述智能体，跑通首轮真实链路。

### 执行流程

```text
后端读取灾前、灾后影像
→ 调用 Agent1
→ 保存建筑/道路 Mask、实例损伤、融合图、证据账本和复核标志
→ 创建 artifacts 记录
→ 调用 Agent2
→ 保存英文变化描述、提示词快照和运行清单
→ 更新 agent_runs
→ 前端显示真实结果
```

### 工作内容

1. 为 Agent1 建立适配器。
2. 为 Agent2 建立适配器。
3. 统一 Agent 返回值和异常格式。
4. 保存模型名称和版本。
5. 保存运行时间和错误信息。
6. 前端由 Mock 结果切换为真实结果。

### 验收条件

- 一组标准影像能完成 Agent1、Agent2。
- 所有输出文件可以从前端访问。
- Agent1 核心统计与直接运行脚本结果一致。
- Agent2 英文描述与 `agent2_output.json` 一致，并显示“尚未经过证据校验”。
- Agent 执行失败不会破坏整个任务记录。

### 讨论确认点

- Agent 是 Python 函数、命令行程序还是独立服务
- GPU 环境位于本地、AutoDL 还是云服务器
- 模型运行时是否允许并发

## 阶段 6：Agent3 和 Agent4 接入

### 目标

完成英文描述证据校验和中文正式报告输出。

### 执行流程

```text
Agent2 英文描述 + Agent1 客观证据
→ Agent3 拆分原子 Claims 并逐条校验
→ Agent3 生成 verified_description_en
→ Agent4 读取校验结果、场景摘要和 review_flags
→ Agent4 生成中文 JSON/Markdown 报告
```

### 关键规则

- Agent3 状态统一为 `supported`、`partially_supported`、`unsupported`、`contradicted`、`exaggerated`。
- `unsupported` 和 `contradicted` 内容不能进入正式结论。
- `exaggerated` 内容必须降级或删除。
- Agent3 不读取 `review_flags.json`，也不输出 `needs_human_review`。
- Agent4 读取 `review_flags.json`，当 `review_required=true` 时必须加入人工复核提示。
- 道路结果只能表述为“疑似受影响”或“可能存在通行受阻风险”。
- 模型置信度不得表述为真实正确概率，必须注明尚未校准。
- 报告必须记录 Agent 和模型版本。
- 人工修改必须记录修改时间和原因。

### 验收条件

- Agent3 能将每条英文描述拆为单一事实 Claims，不漏句、不新增事实。
- 每条 Claim 都有 `status`、`reason`、`evidence_refs` 和 `suggested_revision`。
- Agent4 不会引用已拦截的 Claim。
- 精确数量和比例只来自 Agent1 场景摘要，不来自 Agent2 自然语言。
- 固定20条样本通过 `sample_id` 正确配对。
- 前端可以预览并下载 Markdown 和 JSON。
