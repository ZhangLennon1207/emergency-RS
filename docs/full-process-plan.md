# 可信遥感损毁评估与应急研判多智能体系统全过程实施方案

## 1. 文档目的

本方案用于指导项目从当前前端演示版本，逐步发展为能够接入 Agent1～Agent5、保存真实任务数据、执行可信校验并生成报告的完整系统。

项目采用“先讨论确认、再分阶段实施”的方式。每个阶段完成后进行验收，确认无误后再进入下一阶段，避免前端、后端和 Agent 团队同时修改同一套数据结构。

---

## 2. 最终项目定位

### 项目名称

可信遥感损毁评估与应急研判多智能体系统。

### 核心业务闭环

```text
创建研判任务
→ 上传灾前、灾后遥感影像
→ Agent1 建筑与五级损伤识别
→ Agent2 损伤量化评估
→ Agent3 灾情描述生成
→ Agent4 图文证据可信校验
→ 人工复核高风险结论
→ Agent5 生成 Markdown 和 JSON 报告
→ 前端展示、下载和归档
```

### 五智能体职责

| Agent | 名称 | 核心输出 |
| --- | --- | --- |
| Agent1 | 时空视觉证据感知智能体 | 建筑 Mask、五级损伤 Mask、彩色损伤图、叠加图、`evidence_json` |
| Agent2 | 损伤量化评估智能体 | 建筑面积、各等级像素与比例、主导损伤等级、风险等级、饼图 |
| Agent3 | 灾情描述生成智能体 | 环境变化描述、灾害影响描述、结构化 Claims |
| Agent4 | 证据校验智能体 | `supported`、`unsupported`、`exaggerated`、校验依据 |
| Agent5 | 报告生成智能体 | Markdown 报告、结构化 JSON 报告 |

## 3. 团队边界

### 前端负责

- 任务创建、影像选择和上传交互
- 五智能体执行状态展示
- 灾前灾后影像对比
- 建筑 Mask 和损伤 Mask 图层展示
- 损伤量化图表
- 灾情描述与 Claim 展示
- 证据校验和人工复核界面
- 报告预览、下载和状态管理
- 加载、失败、重试、空数据等页面状态

### 后端负责

- FastAPI 接口
- 用户请求校验
- 任务状态机
- PostgreSQL 数据读写
- MinIO 或 OSS 文件管理
- Agent 调度和结果落库
- 报告文件下载
- 日志、错误码和权限控制

### Agent 团队负责

- 影像预处理和模型推理
- Agent1～Agent5 内部实现
- 每个 Agent 输入、输出符合约定格式
- 输出文件和结构化 JSON
- 模型版本、运行时间和错误信息

### 重要原则

- 前端不能直接连接数据库。
- Agent 不直接向业务数据库写表。
- Agent 结果统一返回给后端，由后端落库和上传文件。
- TIFF、Mask、模型权重和报告文件不保存到 PostgreSQL。
- 前端不依赖 Agent 本地目录结构，只依赖 API 返回的数据和文件 URL。

## 5. 总体技术架构

```text
React 前端
    │
    │ HTTP / WebSocket
    ▼
FastAPI 后端
    ├── PostgreSQL + PostGIS：任务、状态、统计、Claim、报告元数据
    ├── MinIO / OSS：遥感影像、Mask、图表、JSON、Markdown
    ├── Redis：异步任务队列和临时进度
    └── Agent 编排服务
            ├── Agent1
            ├── Agent2
            ├── Agent3
            ├── Agent4
            └── Agent5
```

开发阶段允许先不使用 Redis。后端可以通过后台任务或简单任务执行器完成第一轮联调，确认模型耗时和并发需求后再决定是否引入 Celery、RQ 或其他任务队列。

## 6. 全过程实施阶段

## 阶段 0：需求和数据契约冻结

### 目标

先统一“系统传递什么数据”，再继续扩展页面和后端。

### 工作内容

1. 确认灾害类型：
   - 地震
   - 洪水
   - 台风
   - 山火
   - 爆炸
   - 火灾
   - 化学泄漏
   - 冲突战损
2. 确认损伤等级 0～4 的正式中文名称和颜色。
3. 确认任务状态、Agent 状态、风险等级和报告状态。
4. 确认 Agent1～Agent5 的输入输出 JSON。
5. 确认文件类型、命名规则和目录规则。
6. 编写 `docs/api-contract.md`。
7. 准备一套完整的标准演示样本。

### 交付物

- API 契约文档
- 枚举字典
- Agent 输入输出示例
- 标准任务 Mock JSON
- 标准成果文件清单

### 验收条件

- 前端、后端和 Agent 成员均确认字段含义。
- 同一个概念不再出现多套英文名称。
- JSON 示例能够完整覆盖五个 Agent。

### 讨论确认点

- 五级损伤正式定义
- Agent3 是否直接输出 Claims
- Agent4 输入是完整描述还是拆分后的 Claims
- Agent5 报告由后端模板生成还是 Agent 独立生成

5. 实现建筑 Mask 显示和隐藏。
6. 实现损伤 Mask 透明度调节。
7. 实现 0～4 级损伤图例。
8. 实现 Agent2 数量、面积、比例和风险统计。
9. 展示 Agent3 描述和结构化 Claims。
10. 支持查看和下载原始 JSON。

### 交付物

- 完整结果分析页面
- 影像对比组件
- 图层控制组件
- 损伤统计组件
- 灾情描述组件

### 验收条件

- 用户能从任务详情进入结果分析。
- 五个结果标签均可使用。
- 图层控制不会导致页面明显卡顿。
- 页面使用 Mock 数据也能完整演示。

## 阶段 2：新建任务和上传流程完善

### 目标

让任务创建页面具备真实系统所需的输入校验和交互状态。

### 工作内容

1. 灾前、灾后影像缩略图预览。
2. 文件类型、文件大小和文件名称校验。
3. 防止灾前、灾后选择同一个文件。
4. 支持移除和重新选择文件。
5. 展示上传进度、成功和失败状态。
6. 增加任务名称、灾害类型、地点和备注。
7. 预留坐标系、拍摄时间和传感器信息字段。
8. Mock 模式模拟上传过程。

### 验收条件

- 无效文件不能提交。
- 未完成必填信息时按钮不可用。
- 上传失败后可以重试。
- 页面刷新或返回时不会产生误提交。

### 讨论确认点

- 支持的文件格式
- 单文件最大体积
- 是否接受压缩包
- 是否需要输入坐标系和影像分辨率

## 阶段 3：前端工程化和 API 切换

### 目标

让前端能在 Mock 和真实 FastAPI 之间切换。

### 工作内容

1. 将 Mock 数据和 API 请求拆分。
2. 建立统一 `apiClient`。
3. 建立以下服务：
   - `taskService`
   - `uploadService`
   - `agentService`
   - `resultService`
   - `evidenceService`
   - `reportService`
4. 增加环境变量：

```text
VITE_USE_MOCK=true
VITE_API_BASE_URL=/api/v1
VITE_WS_URL=/ws
```

5. 统一请求超时、错误提示和重试。
6. 增加骨架屏、空状态和错误状态。
7. 接口返回结构统一转换为前端模型。

### 验收条件

- `VITE_USE_MOCK=true` 时不依赖后端。
- `VITE_USE_MOCK=false` 时所有请求进入 FastAPI。
- 页面组件不包含后端地址。
- 页面组件不直接处理 Token。

## 阶段 5：Agent1 和 Agent2 首轮接入

### 目标

先接入结构最明确的视觉感知和损伤量化，跑通真实模型链路。

### 执行流程

```text
后端读取灾前、灾后影像
→ 调用 Agent1
→ 保存建筑 Mask、损伤 Mask 和证据图
→ 创建 artifacts 记录
→ 调用 Agent2
→ 保存损伤统计
→ 更新 agent_runs
→ 前端显示真实结果
```

### 工作内容

1. 为 Agent1 建立适配器。
2. 为 Agent2 建立适配器。
3. 统一 Agent 返回值和异常格式。
4. 保存模型名称和版本。
5. 保存运行时间和错误信息。
6. 前端由 Mock 结果切换为真实结果。

### 验收条件

- 一组标准影像能完成 Agent1、Agent2。
- 所有输出文件可以从前端访问。
- Agent2 统计与 Mask 数据一致。
- Agent 执行失败不会破坏整个任务记录。

### 讨论确认点

- Agent 是 Python 函数、命令行程序还是独立服务
- GPU 环境位于本地、AutoDL 还是云服务器
- 模型运行时是否允许并发

---

## 阶段 6：Agent3、Agent4 和 Agent5 接入

### 目标

完成描述生成、证据校验和报告输出。

### 执行流程

```text
Agent1/2 结构化结果
→ Agent3 生成描述和 Claims
→ Agent4 对每条 Claim 校验
→ 高风险 Claim 进入人工复核
→ Agent5 只使用可信结果生成报告
```

### 关键规则

- `unsupported` 内容不能进入正式结论。
- `exaggerated` 内容必须降级或删除。
- `pending_review` 内容必须等待人工处理。
- 报告必须记录 Agent 和模型版本。
- 人工修改必须记录修改时间和原因。

### 验收条件

- Agent3 描述可以拆分为可校验 Claims。
- Agent4 每条判定都有证据和理由。
- Agent5 不会引用已拦截的 Claim。
- 前端可以预览并下载 Markdown 和 JSON。

---

## 阶段 7：任务队列和实时进度

### 目标

解决模型执行时间长、请求超时和并发任务问题。

### 工作内容

1. 确认任务执行方式：
   - FastAPI 后台任务
   - Redis + Celery
   - Redis + RQ
   - 独立 Agent Worker
2. 建立统一任务状态机。
3. 增加 Agent 超时和重试。
4. 增加任务取消。
5. 前端先使用轮询获取进度。
6. 任务量增加后再切换 WebSocket。

### 推荐顺序

```text
第一版：每 2 秒轮询
→ 验证真实任务耗时和稳定性
→ 再决定是否增加 WebSocket
```

### 验收条件

- 关闭浏览器不会中断后端任务。
- 刷新页面后可以继续查看进度。
- Agent 失败后可以定位具体阶段。
- 重试不会重复创建无效成果。

- 只有授权人员能覆盖 AI 结果。
