# Emergency RS 前端完善实施方案

## 1. 当前状态

当前前端已经具备完整的指挥中心视觉风格，但本质上仍是静态演示页面：

- `src/App.jsx` 集中了页面结构、模拟数据和图表配置，文件较大，不利于多人协作。
- 左侧五个导航项只是按钮，没有独立页面和路由。
- 搜索、筛选、生成简报、导出 JSON、人工复核等操作尚未实现。
- 业务数据全部硬编码，尚未形成统一的数据模型和 API 调用层。
- 缺少加载、空数据、错误、权限不足、推理进行中等业务状态。
- 尚未建立前端测试、环境变量和接口联调规范。

前端完善的目标不是单纯增加页面，而是把现有展示稿升级成一个可以独立演示、后续能够平滑连接 FastAPI 后端的业务前端。

---

## 2. 建设目标

第一阶段完成后，前端应具备以下能力：

1. 五个导航入口均有独立页面和可分享的 URL。
2. 核心业务链路可以使用模拟数据完整演示。
3. 所有页面统一通过服务层获取数据，不再直接依赖硬编码数组。
4. 后端接口准备好后，只需切换数据源，不需要重写页面。
5. 桌面端适配指挥大屏，平板和普通笔记本可正常使用。
6. 页面具备加载、错误、空状态、操作反馈和二次确认。
7. 项目能够通过代码检查、生产构建和关键流程测试。

## 3. 页面信息架构

### 3.1 登录页 `/login`

第一版可以提供演示登录，后续接入 JWT。

主要内容：

- 平台品牌和系统简介
- 用户名、密码、记住登录状态
- 登录失败提示
- 演示账号提示
- 登录中的禁用状态

### 3.2 态势总览 `/overview`

在现有首页基础上完善，负责回答“现在发生了什么”。

主要内容：

- 总体运行状态和数据更新时间
- 洪涝热区、待复核、已闭环、AI 研判耗时等 KPI
- 24 小时事件识别与核验趋势
- 置信度分布
- 在办事件列表
- 重点区域小地图
- 事件搜索与条件筛选
- 点击事件后进入事件详情

### 3.3 区域监测 `/regions`

负责回答“灾害发生在哪里、范围多大”。

主要内容：

- 地图与区域列表联动
- 灾前、灾后、变化掩码图层切换
- 按地区、灾害类型、严重度、置信度筛选
- 区域详情抽屉
- 面积、中心点、受影响道路和建筑等指标
- 发起 AI 研判
- 标记为待复核或安全区域

地图第一版建议使用 Leaflet；如果后续需要三维地球、大规模瓦片或专业遥感图层，再评估 MapLibre GL 或 Cesium。

### 3.4 证据链中心 `/evidence`

负责回答“结论依据是什么”。

主要内容：

- 灾前影像、灾后影像、变化图和分割掩码并排对比
- 图像缩放、拖动、透明度调整
- 变化检测、语义分割、主动验证、证据成文四步时间线
- 每一步的模型、参数、时间和置信度
- 不确定性原因说明
- 人工复核意见和操作记录
- 证据导出

### 3.5 智能研判 `/agent`

负责回答“模型正在做什么、结果是否可信”。

主要内容：

- 选择事件、区域和灾前灾后影像
- 上传影像或从已有影像中选择
- 创建研判任务
- 展示排队、处理中、成功、失败状态
- 实时进度和阶段日志
- 灾害类型、严重度、置信度和推理说明
- 低置信结果必须进入人工复核
- 支持重新研判和参数调整

### 3.6 报告中心 `/reports`

负责回答“如何把结果交付给指挥人员”。

主要内容：

- 报告列表、状态和创建人
- 报告预览
- 事件摘要、受灾区域、证据链、风险提示、处置建议
- 编辑标题和文字说明
- 发布前检查
- 导出 PDF、Word 或 JSON
- 报告版本和发布时间

### 3.7 事件详情 `/incidents/:incidentId`

该页面不一定放在侧边导航中，但应作为各页面之间的业务连接点。

主要内容：

- 事件基本信息和状态流转
- 关联区域和地图
- 研判结果
- 证据链
- 处置记录
- 关联报告

## 4. 推荐前端结构

```text
src/
├── app/
│   ├── router.jsx
│   └── providers.jsx
├── layouts/
│   └── AppShell.jsx
├── pages/
│   ├── LoginPage.jsx
│   ├── OverviewPage.jsx
│   ├── RegionsPage.jsx
│   ├── EvidencePage.jsx
│   ├── AgentPage.jsx
│   ├── ReportsPage.jsx
│   └── IncidentDetailPage.jsx
├── components/
│   ├── common/
│   ├── dashboard/
│   ├── map/
│   ├── evidence/
│   ├── agent/
│   └── reports/
├── services/
│   ├── apiClient.js
│   ├── dashboardService.js
│   ├── incidentService.js
│   ├── regionService.js
│   ├── assessmentService.js
│   ├── evidenceService.js
│   └── reportService.js
├── mocks/
│   ├── data/
│   └── handlers.js
├── hooks/
├── utils/
├── constants/
├── styles/
└── assets/
```

拆分原则：

- 页面组件负责组织业务，不直接写请求细节。
- 服务层负责 API 地址、参数和响应转换。
- 通用组件只处理展示和交互，不包含特定业务数据。
- 模拟数据与页面分离，字段结构与未来后端响应保持一致。
- 不追求一次拆得过细；稳定复用两次以上的模块再抽成通用组件。

## 5. 技术选型

### 必需依赖

| 需求 | 建议 |
| --- | --- |
| 页面路由 | `react-router-dom` |
| 请求管理 | `@tanstack/react-query` |
| HTTP 客户端 | 原生 `fetch` 封装或 `axios`，二选一 |
| 表单与校验 | `react-hook-form` + `zod` |
| 地图 | `leaflet` + `react-leaflet` |
| 日期处理 | `dayjs` |
| 消息提示 | 轻量 Toast 组件 |
| 测试 | `vitest` + `@testing-library/react` |
| API 模拟 | `msw` |

### 状态管理原则

- 服务端数据交给 React Query 管理，包括缓存、刷新、失败重试和加载状态。
- 登录用户、主题和侧边栏折叠等少量全局状态使用 React Context。
- 表单状态留在表单组件内部。
- 第一阶段不引入 Redux，避免不必要的复杂度。

## 6. 数据接入策略

前端采用“同一接口、两种数据源”：

```text
页面组件
   ↓
Service 服务层
   ↓
开发阶段：MSW 模拟 API
联调阶段：FastAPI /api/v1
```

环境变量：

```text
VITE_API_BASE_URL=/api/v1
VITE_USE_MOCK=true
VITE_WS_URL=/ws
```

统一响应建议：

```json
{
  "data": {},
  "message": "success",
  "request_id": "req_xxx"
}
```

列表响应建议：

```json
{
  "data": {
    "items": [],
    "page": 1,
    "page_size": 20,
    "total": 0
  }
}
```

前端与后端必须统一以下枚举，避免页面中散落中英文判断：

- 灾害类型
- 严重度
- 置信度
- 事件状态
- 研判任务状态
- 报告状态
- 用户角色

## 7. 统一交互规范

每个页面都需要覆盖以下状态：

- 首次加载：骨架屏，不使用空白页面。
- 局部刷新：保留旧数据并显示刷新状态。
- 空数据：说明原因并给出下一步操作。
- 请求失败：显示可理解的错误和重试按钮。
- 无权限：隐藏危险操作并显示权限说明。
- 操作成功：Toast 提示并刷新关联数据。
- 危险操作：删除、覆盖研判结果、发布报告需要二次确认。
- 异步任务：展示排队、处理中、成功、失败和取消状态。

重要规则：

- 不确定结果不能直接进入“已确认”报告。
- 人工修改 AI 结果必须留下修改人、时间和原因。
- 所有时间统一显示时区，并提供完整时间提示。
- 图表颜色、标签颜色和地图颜色使用同一套灾害语义。

## 8. 视觉与响应式完善

保留现有“深色侧栏 + 浅色工作区”的设计方向，在此基础上建立设计变量：

- 主色、成功、警告、危险、信息色
- 页面背景、卡片背景、边框和阴影
- 字号、字重和行高
- 8px 间距体系
- 8px、12px、16px、24px 圆角等级
- 图表和地图的统一图例

建议断点：

- `>= 1440px`：完整指挥台布局
- `1024px - 1439px`：压缩侧栏和卡片间距
- `768px - 1023px`：侧栏折叠，双栏变单栏
- `< 768px`：只保障查看和轻量操作，不承载复杂影像研判

同时补充：

- 键盘焦点样式
- 图标按钮的文字说明
- 表单标签和错误提示
- 对比度检查
- `prefers-reduced-motion` 动画降级

## 9. 分阶段实施计划

### 阶段 0：基线修复与约定（1～2 天）

1. 确认中文文件统一使用 UTF-8。
2. 修复本地 Node/npm 环境并跑通 `lint` 和 `build`。
3. 整理业务枚举、命名和前后端字段约定。
4. 建立 `.env.example` 和开发说明。

交付标准：现有页面可稳定构建，团队使用同一套字段和编码规范。

### 阶段 1：前端骨架重构（2～3 天）

1. 引入 React Router。
2. 抽离 `AppShell`、侧边栏、顶部栏和通用面板。
3. 将现有总览迁移到 `OverviewPage`。
4. 建立路由占位页面和 404 页面。
5. 建立 React Query、Service 层和统一错误处理。

交付标准：五个导航均可访问，现有总览视觉基本不变，`App.jsx` 只保留应用入口职责。

### 阶段 2：模拟 API 与总览可交互（3～4 天）

1. 使用 MSW 建立与后端一致的模拟接口。
2. 总览页数据改为异步获取。
3. 实现搜索、筛选、刷新和事件跳转。
4. 完成加载、空状态和失败重试。
5. 增加事件详情页。

交付标准：关闭后端也能完整演示总览和事件详情，页面中不再直接保存业务数组。

### 阶段 3：核心业务页面（7～10 天）

1. 完成区域监测地图和图层控制。
2. 完成证据链影像对比和步骤时间线。
3. 完成智能研判任务创建、进度和结果页。
4. 完成报告列表、预览和发布前检查。
5. 打通事件 → 区域 → 研判 → 证据 → 报告的页面跳转。

交付标准：使用模拟数据可跑通完整业务闭环。

### 阶段 4：后端联调（4～7 天）

1. 切换 FastAPI 数据源。
2. 接入登录、Token 刷新和权限控制。
3. 统一错误码和字段转换。
4. 接入文件上传、任务轮询或 WebSocket。
5. 处理大图加载、请求取消和超时。

交付标准：核心页面使用真实接口，刷新页面后登录和页面状态符合预期。

### 阶段 5：质量与发布（3～5 天）

1. 为关键组件和服务层补充单元测试。
2. 为登录和完整研判链路补充端到端测试。
3. 检查响应式、无障碍和浏览器兼容。
4. 分析构建体积并进行路由懒加载。
5. 完成生产环境变量、错误监控和发布检查表。

交付标准：`lint`、测试和生产构建全部通过，关键演示流程无阻断问题。

## 10. 第一轮开发建议

第一轮优先完成下面十项，不建议立即堆叠全部页面细节：

1. 修复并确认构建环境。
2. 安装 React Router 和 React Query。
3. 建立 `AppShell` 和路由。
4. 将总览页从 `App.jsx` 拆出。
5. 建立通用 `Panel`、`StatusTag`、`EmptyState`、`ErrorState` 和 `Skeleton`。
6. 建立业务枚举和显示文本映射。
7. 建立 Service 层。
8. 用 MSW 提供总览和事件接口。
9. 完成事件详情页。
10. 对第一轮结果进行视觉和构建验收。

完成这一轮后，再由区域监测、证据链、智能研判、报告中心四块并行开发，团队成员之间的文件冲突会明显减少。

## 11. 验收清单

### 功能

- 五个导航页面均可访问，刷新后路由不丢失。
- 搜索和筛选能够影响列表与地图。
- 事件详情能关联区域、研判、证据和报告。
- 低置信度结果无法未经复核直接发布。
- 上传和异步研判过程有明确进度与失败处理。

### 质量

- 页面不直接硬编码后端地址。
- 页面组件不直接拼接 Token。
- 没有控制台报错和明显布局溢出。
- 慢网络和接口失败时页面仍可操作。
- 关键流程有自动化测试。
- `npm run lint`、`npm run test`、`npm run build` 全部通过。

### 演示

- 无后端时可使用 Mock 模式演示。
- 有后端时只需修改环境变量即可切换。
- 一次完整演示可在 5～8 分钟内走完：
  态势总览 → 事件详情 → 区域查看 → AI 研判 → 证据复核 → 报告发布。

## 12. 风险与规避

| 风险 | 处理方式 |
| --- | --- |
| 后端字段持续变化 | 先冻结接口契约，Service 层负责转换 |
| 遥感大图导致页面卡顿 | 缩略图、瓦片、懒加载、Web Worker 分阶段引入 |
| 单个页面继续膨胀 | 按业务区域拆组件，数据请求集中到页面或自定义 Hook |
| 团队并行开发冲突 | 先完成骨架和公共组件，再按页面分工 |
| 模型任务耗时较长 | 使用任务状态机、轮询或 WebSocket，不让请求长时间挂起 |
| 演示环境后端不稳定 | 保留 Mock 模式和演示数据快照 |
